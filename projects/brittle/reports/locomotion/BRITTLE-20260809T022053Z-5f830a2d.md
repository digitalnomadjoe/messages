## Verdict

# `TEMPO SIGNAL NOT LICENSED`

**The one reason:** `p_tempo`'s target is a **c-independent scalar**, so its equilibrium is a
**single cadence — 0.852 Hz — for every command.** Enabling it would *flatten* the cadence axis,
not track it. It cannot supply a cadence-ordered learning signal because it does not know the
cadence.

---

## 1. The target is a scalar, and that is decisive

```
train_tip_reftrack.py:797   self.ss_target_frames = float(ss_target_s) / 0.02   # 0.55/0.02 = 27.5 frames
```

`ss_target_frames` appears on the left of an assignment **exactly once** in the whole trainer.
It is never made per-world. The per-world cadence target `1/c_w` is wired somewhere else
entirely — `sim.set_rp_step_period_w` (`:4581`) — which the trainer's **own comment** calls
*"NOT a new reward term"*.

What dwell each cadence actually needs, measured from each reference member's own contact
schedule:

| `c_cmd` | reference SS dwell | constant target | error |
|---|---|---|---|
| 0.70 | **0.670 s** | 0.550 s | **+0.120 s** |
| 0.85 | **0.550 s** | 0.550 s | **0.000 s** |
| 1.00 | **0.470 s** | 0.550 s | **−0.080 s** |

The default `ss_target_s = 0.55` is exactly right for **c = 0.85 and nothing else** — it was
tuned for a single-cadence lane and never generalised.

**The equilibrium this implies, computed rather than asserted:**

```
reference dwell × cadence :  0.670×0.70 = 0.4690
                             0.550×0.85 = 0.4675      duty constant k = 0.4688
                             0.470×1.00 = 0.4700
a constant 0.550 s dwell target  =>  cadence = k / 0.550 = 0.852 Hz   FOR EVERY WORLD
```

Whatever `c_cmd` says, this term pulls toward ~0.85 Hz. **That is the cadence axis collapsing to
a point.**

## 3. Required direction — passes on ordering, fails on equilibrium

**Ordering: CORRECT.** |`p_tempo`| is 432 > 310 > 113 across c = 0.70 / 0.85 / 1.00. The
worst-inverted cell is penalised most, in both seed and CY.

**Direction: correct only until it overshoots.** All three cells currently step too fast, so the
penalty pushes cadence *down*, which is toward command for all three. But it does not stop at the
command — it stops at 0.852 Hz:

| `c_cmd` | realized now | where `p_tempo` pulls it | toward or past command? |
|---|---|---|---|
| 0.70 | 1.8868 | 0.852 | toward, then **overshoots past 0.70 → 0.85** |
| 0.85 | 1.5737 | 0.852 | **toward, and correct** |
| 1.00 | 1.0732 | 0.852 | **starts toward, ends ~15 % BELOW command** |

The ticket asked not to accept "merely nonzero" and to require the ordering to move realized
cadence *toward command*. It does that for one of three cells and breaks a cell that is currently
within 0.073 Hz of its command. **A term that would drag the visually-passed c = 1.00 gait 15 %
below its own command is not a cadence-tracking signal.**

## 4. Collateral — every candidate weight dominates the objective

Term ledger from the run (per-episode means): `track` +8.12, `r_yaw` +7.97, `r_fwd` +6.16,
`track_feet` +2.24, `track_jnt` +3.24, `p_cap` −0.08, `p_slip` −0.17, `fall_cost` −50.0.
**Whole positive reward sum: +23.97.**

| weight | \|`p_tempo`\| per episode (c=0.70 / 0.85 / 1.00) | ×  the entire positive reward sum |
|---|---|---|
| **0.5** | 216.0 / 155.0 / 56.5 | **9.0× / 6.5× / 2.4×** |
| **1.0** | 432.0 / 310.0 / 113.0 | 18.0× / 12.9× / 4.7× |
| **3.0** | 1296.0 / 930.0 / 339.0 | 54.1× / 38.8× / 14.1× |

**At the smallest candidate weight the penalty is already 2.4–9.0× the entire positive reward and
4.3× the fall cost.** A policy optimising this would minimise single-support time by any means
available — including not walking. This is an independent, sufficient reason to reject all three
weights, and it would plausibly destroy the visually-passed walking basin.

## 5. Curvature — the dwell proxy is ambiguous under turning

| κ | R-foot SS dwell | L-foot SS dwell | asymmetry |
|---|---|---|---|
| +0.60 | 0.320 s | 0.410 s | **0.090 s (24.7 %)** |
| −0.60 | 0.300 s | 0.360 s | **0.060 s (18.2 %)** |

Turning legitimately makes the inside and outside feet dwell differently by up to a quarter. A
single scalar target cannot tell "turning" from "wrong cadence" and would tax the difference as a
tempo error — so this term would also fight **curvature**, the one command axis that currently
works.

## 6. Budget — no budget is recommended for this term

Because the signal is not licensed, **no acquisition budget is recommended and none should be
authorised for `p_tempo` as it stands.** Spending any budget on it would test a term whose
optimum is the wrong gait.

Recorded for whenever a *corrected*, per-world tempo term exists (a separate change, not
proposed here and not made): the previous non-result was **3 iterations**. A bounded test able to
show whether an inherited prior can move at all is on the order of **30 iterations ≈ 4.4 M env
steps** (30 × 147,456), with a mid-run checkpoint so basin damage is caught before the full spend,
and staying well inside the imitation-anchor decay horizon of 8,388,608 steps so the anchor is
still active. That is an estimate for a term that does not yet exist — **not a license.**

## 7. What would make it licensable

One sentence, since the ticket forbids proposing changes beyond the probe: the term needs its
target to be **per-world and cadence-derived** — the quantity `k / c_w` with `k ≈ 0.4688`
measured above — and a weight set from the measured penalty scale rather than from the `a4`
preset, which was tuned against a completely different reward magnitude.

**The RCA's recommended repair is therefore withdrawn as stated.** Enabling `ss_tempo_w` alone
would not have supplied a cadence-learning signal; it would have collapsed the axis and very
likely broken the gait. Finding that out cost one probe and no training.

**No PPO. No reward edit. No reference, gait or command-interface change. Nothing launched.**
