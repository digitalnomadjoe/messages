buy cadence. The reward economy has moved the coupling to the other axis rather than removing it.

## 7. ⚠ Recommendation on the heldout qualification: **HOLD**

**Do not run the heldout speed × cadence × curvature qualification on this checkpoint yet.**

The heldout set exists (12 cells, including the untrained cadences 0.90/0.925/0.95) and it
measures *generalisation*. Running it now would measure how a policy generalises when it does not
meet its speed spec **on the training surface it was optimised for** — mean |speed err| 0.0220
across 22 members, max 0.0556, and the fixed-v triplet out of band at 0.0272. A heldout PASS
would be misleading and a heldout FAIL would not tell us whether the cause is generalisation or
the in-distribution speed regression. The measurement would not be decidable either way.

**What I would fix first, stated and not acted on:** the coupling has moved from cadence→speed to
speed→cadence, and §6 shows it is a continuous trade rather than an artifact of where training
stopped. That points at the **weight ratio** (cadence 19.5 vs forward-speed 12) as the thing that
now sets the operating point — not at more steps. Probe D already showed that raising
`fwd_dominant_w` alone does not work, because `r_fwd` peaks per *member* and is blind to the
common-mode drift the gate measures. So the candidate is the opposite direction — reduce the
cadence weight — or give the speed term a fixed-command anchor. Both are reward changes and
outside this ticket.

**If you want heldout data now**, run it explicitly labelled as a **diagnostic**, not a
qualification: it would tell us whether the untrained cadences (0.90/0.925/0.95) interpolate,
which is useful independently of the speed regression. I have not run it.

## 8. ⚠ A defect in the frozen gate producer, found by this run

`cadence_slope_gate.py:183` names its checkpoint with `sorted(...)` over filenames, which is
**lexicographic**: `ppo_884736.zip` sorts *after* `ppo_4423680.zip`. Every prior use of the gate
had exactly one checkpoint, so it was latent until this run produced 15.

**The measurements are unaffected** — `RolloutStreamer` selects by parsed step number, and the
spectator log shows `RELOADED_CHECKPOINT ppo_4423680.zip` for every cell. Only the
`checkpoint_sha16` **label** in the receipt is wrong; the gate receipt for this run records
`0e6d6963d15d7acd` (`ppo_884736`) while it actually evaluated `e54bfb171b97cc47`.

My own qualification script had the identical bug; I corrected it and recorded the correction in
its receipt (`checkpoint_label_correction`). **I have not touched the gate producer** — it is a
bound Guard member pinned `1125b30033225ed5` and changing it is a canonical mutation this ticket
does not authorize. Flagging it for a separate decision; until then, any gate receipt from a
multi-checkpoint run has an untrustworthy checkpoint field.
