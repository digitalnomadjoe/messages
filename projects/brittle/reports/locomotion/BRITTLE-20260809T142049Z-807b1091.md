## 2. The re-derived weight — and why 19.5 ships

Rule unchanged, applied to **walking cells only**: the worst walking-cell per-step penalty must
cost no more than one `track_feet` (2.24107). Standing and one-foot hold are measured above but
**excluded from the denominator** — sizing the weight against the behaviour the term exists to
punish would shrink it exactly when it is working.

```
bound   w ≤ track_feet / worst = 2.24107 / 0.11147 = 20.104
derived w = 20.0        (same 0.5 grid that produced 17.5 and 19.5)
```

**The newly derived weight is 20.0.** It is **not adopted**, on three numbers:

| | |
|---|---|
| 19.5 → worst cell costs | **2.1737 = 97.0 %** of one `track_feet` — **COMPLIES** |
| 20.0 → worst cell costs | 2.2295 = 99.5 % — also complies |
| step 19.5 → 20.0 | **+2.56 %** |
| **spread across the six c = 0.70 cells** | **2.21 %** → implied weights **20.10 – 20.56** |
| 19.5 under the **old bare-`f`** numbers | 19.5 × 0.11520 = 2.2464 = **100.2 %** — it had **exceeded** its bound |

Which cell happens to be worst moves the derived weight by **more than the change itself**, so
+2.56 % is not a resolvable difference — it is inside the sampling spread of the quantity it is
derived from. And the correction runs in the safe direction: on bare-`f` data 19.5 sat 0.2 %
**over** the bound; on `g_v1` it sits 3.0 % **under** it.

**At 19.5 the worst cell is 97.0 % of `track_feet`, 67.0 % of `track_jnt`, 9.07 % of the positive
per-step sum, and 4.35 % of the fall cost** — meaningful, and subordinate to the walking basin on
every comparison the original licence named.

If you would rather sit at the bound, **20.0 also complies** and the receipt carries both
(`kept_weight` and `at_final_weight`); say so and I re-pin. Nothing else in the package moves —
the trainer, reward book, runtime reward contract, slope gate and construction digest are all

## 4. ⚠ A second defect, found while re-testing: the argv gate depended on the ambient `grep`

The membership test was `printf '%s\n' "${TRAINER_ARGS[@]}" | grep -qxF -- "$flag"`. Re-running the
dry through the real card, it **refused a correct argv**, claiming `--exact-symmetry-matrices` was
missing while the flag was plainly in the array.

Cause: **`grep` here is a shell function wrapping `ugrep` 7.5.0**, exported from the session's
shell snapshot — and `ugrep` is not even resolvable in a non-interactive shell. So the gate's
verdict was a function of the caller's PATH and function table, not of the argv. That cuts both
ways: it can refuse a good run, and a `grep` that returns 0 would have **passed a bad one**.

**Fixed by removing the dependency**, not by pinning a `grep`. Membership is now string equality
over the array in pure bash — no external tool, nothing to resolve:

```bash
_has_flag () { local n="$1" a; shift; for a in "$@"; do [ "$a" = "$n" ] && return 0; done; return 1; }
```

Test suite extended to **12/12** on the block extracted verbatim from the launcher, with three
regressions aimed squarely at this failure — each of which the old `grep` form would have failed:

| | rc |
|---|---|
| control · 6 flag/value mutants · 2 missing-value mutants (from row 115) | 0 · 3 · 3 |
| **ambient `grep` ALWAYS FAILS → correct argv still accepted** | **0** |
| **ambient `grep` ALWAYS SUCCEEDS → missing `--cadence-track-w` still refused** | **3** |
| **`grep` removed from PATH entirely → correct argv still accepted** | **0** |

Verified end-to-end through a real `TC_MODE=dry` on a separate scratch OUT:

```
[card] argv assertions OK on the REAL trainer argv: --exact-symmetry,
       --exact-symmetry-matrices=$BANK, --cadence-track-w=19.5
[card] RESOLVED CONFIG OK (from reward_book): cadence_track_w=19.5  ss_tempo_w=0.0
[card] ===== NO OPTIMIZER STEP =====     no ppo_*.zip written
[card] cleanup: closed exact pid 4088991
```

`rl/runs/walking/cy_cadsign_s0` — the real run's OUT — **does not exist**.

This is the same class of finding as row 115's self-grep: a check that appears to test the argv
but actually tests something else. Both are now gone from this launcher.
