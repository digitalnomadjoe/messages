## 1 · The defect, at source

| | TRAINER (`train_tip_reftrack.py`) | EVAL / DEPLOY RUNTIME (`runtime_port.py`) |
|---|---|---|
| cadence at vx 0.272219 | `cadence_cmd` = branch = **0.717721** | `cad` = `clip(2.1475·vx+0.4846, .7, 1)` = **1.000000** (lines 134, 190 — no branch) |
| what the policy READS as obs[53] | `cadence_cmd/2` = **0.35886** (line 1840) | `cad/2` = **0.50000** (line 195) |
| cyclic phase clock | `csphi += cadence_cmd·dt` (0.7177 Hz) | `csphi += cad·dt` (1.0 Hz) |
| reference-pose phase | `_rate = cadence_cmd / c_member` = 0.717721/0.717720 ≈ **1.0** | `cp54_acc += cad/native` — **written at line 191 and never read anywhere**; the eval runtime has no reference-pose playback |

Because `cp54_acc` is dead state, the *only* cadence channels that reach the policy in evaluation are obs[50]/[51] (from csphi) and obs[53]. Both are wrong under the branch, and the pose-phase concern that would have complicated the comparison does not exist. That is what makes the corrected measurement below faithful rather than approximate.

I introduced this in WALK-DR06G: the branch was added to the trainer under your approval, the card records it in the run's `runtime_manifest.json`, but `runtime_port.py` — which is banked and which I correctly did not modify — reads only the four-value `command.cadence_schedule` and ignores any branch key. The DR06G card's fail-closed "read the repair back from `resolved_config`" discipline did not cover it either, because the trainer serializes **neither** `cadence_schedule` nor `cadence_schedule_branch` into `resolved_config.json` (verified: DR06G's own resolved config contains no cadence-schedule key at all). So nothing in the DR06G evidence chain could have caught this, and nothing did.
